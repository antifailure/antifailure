Four things worth knowing:
{{ if kindIs "invalid" .Values.config.signinAllowlist }}
  SIGN IN IS OPEN. Any GitHub account in the world may sign in, because
  config.signinAllowlist is unset, and the application reads an unset allowlist
  as open. That is the right answer only if your network already decides who
  reaches this. Otherwise set config.signinAllowlist to the logins that may
  sign in, or to an empty list to close it to everybody.
{{- else if eq (len .Values.config.signinAllowlist) 0 }}
  Sign in is CLOSED TO EVERYBODY. config.signinAllowlist is set and names
  nobody, which is a real answer and not the same as leaving it unset.
{{- else }}
  Sign in is restricted to {{ len .Values.config.signinAllowlist }} account(s) by config.signinAllowlist.
{{- end }}

  Partition maintenance: {{ .Values.maintenance.mode }}.
{{- if eq .Values.maintenance.mode "cronjob" }}
  The Deployment holds no DDL credential. Only the bootstrap Job and the
  maintenance CronJob do. That is deliberate: a role that can ALTER TABLE can
  drop the policies that isolate tenants, and the pods exposed to traffic
  should not be holding one.
{{- else if eq .Values.maintenance.mode "inProcess" }}
  Every serving replica holds a credential that can ALTER TABLE, because that
  is what maintenance.mode=inProcess means. maintenance.mode=cronjob moves that
  work to a Job and takes the credential out of the serving pods.
{{- else }}
  maintenance.mode is off, so NOTHING in this release keeps the event
  partitions ahead of the writes. A range-partitioned table with no partition
  for an incoming row does not slow down, it fails. Something outside this
  chart must be doing it.
{{- end }}
