# 14.9, partitioning: the decision, and the dead end it came out of

Built, reverted, and built again. The second version is in the tree. This
records why the obvious design cannot work, so that nobody reaches for it a
third time.

## The constraint that decides everything

Ingestion depends on a unique constraint to make a retry safe:

    INSERT INTO events (...) VALUES (...)
    ON CONFLICT (org_id, idempotency_key, occurred_at) DO NOTHING

An engine that sent a batch and lost the response has no way to know which half
landed, so it sends the same batch again and the second copy is dropped by the
database rather than by anything the sender has to get right.

Postgres will not enforce a unique constraint that omits the partition key. So
the partition column is necessarily part of that key, and the only question
worth asking is which column can be in it without breaking it.

## Why `received_at` cannot be the answer

`received_at` is assigned here, by `now()`, at the moment the row is written. It
differs between an attempt and its retry. Put it in the key and the conflict
never fires: every retry inserts a second copy.

The first attempt at 14.9 did exactly this. Twelve ingestion tests went red
immediately with *there is no unique or exclusion constraint matching the ON
CONFLICT specification*, which is the only good thing about it. Silently
accepting duplicates would have been far worse.

## Why `occurred_at` is

`occurred_at` is assigned by the sender when the event happened. The engine
stamps it once, `toWire` passes it through unchanged, and a resend carries the
same value. It does not vary between attempts, so putting it in the key costs
nothing.

Partitioning on a value a client supplies usually invites a skewed clock to
invent partitions forever. That was already handled before this work started:
ingestion rejects `occurredAt` more than a day in the future or more than a year
in the past, so the live range is bounded at `[now - 1 year, now + 1 day]` no
matter what a sender claims.

## The cost, stated plainly

The idempotency key is now `(org_id, idempotency_key, occurred_at)` rather than
`(org_id, idempotency_key)`. A sender that reuses an identifier under a new
timestamp gets two rows where it used to get one.

No sender does that by accident: the identifier and the timestamp are minted
together and resent together. But it is a real difference and it is pinned by a
test that says so, rather than left to be discovered.

## The other options, and what each would have cost

These were the four written down after the first attempt failed. They are kept
because the reasoning is still what rules them out.

**A separate key table.** Keep `events` partitioned and move the uniqueness to a
small unpartitioned `event_keys(org_id, idempotency_key)` written in the same
transaction. Idempotency stays exact, including across a changed timestamp. The
cost is a second write per event and a table that grows without end, which is
the problem partitioning was for. This is the fallback if the weakening above
ever turns out to matter.

**Per-partition idempotency.** Accept that a duplicate is only caught within the
month it arrived in. Strictly worse than the chosen design, which catches it
whenever the retry arrives.

**Partition on something already in the key.** This is what was chosen, once it
became clear `occurred_at` was already in the row and already bounded.

**Do not partition.** Manage size with retention deletes and accept the bloat.
The operations that hurt are exactly the ones partitioning avoids.

## What is in the tree

- `web/packages/db/migrations/0011_partition_events.sql` converts the table,
  moves the existing rows, and restores the grants and the isolation policy that
  recreating the table dropped. Partitions carry the policy too, so a query
  naming one directly is isolated by the same rule.
- `web/packages/db/src/partitions.ts` plans and applies partitions, prunes the
  default by age, and streams a month out for archival.
- `web/apps/api/src/maintenance.ts` runs a pass at startup and daily, as the
  migration role, on a connection opened for the pass and closed after it.
- `docs/src/content/docs/reference/control-plane.md` documents every variable,
  and a test fails if that page and the source disagree in either direction.

## The orderings that are proven

| Ordering | Outcome |
| --- | --- |
| Pass runs, then a write | Row goes in the month it occurred in |
| Pass runs twice | Second is a no-op |
| Two passes at once | Each month created exactly once; the loser treats 42P07 as success |
| Write, then a pass, for a month that does not exist | Row lands in the default partition, the pass creates the month and moves it in |
| Retry arrives two months after the attempt | Dropped as a duplicate, and stays in the month it occurred in |
| Same identifier, different timestamp | Two rows, deliberately, pinned by a test |
| Archive fails, retention is set | Nothing is dropped, the events survive, the failure is reported |
| Archive succeeds | File is complete before the drop; no `.partial` left behind |
| A pass throws | Logged, and the schedule continues |

The negative control for the whole design: switching the partition column back
to `received_at` makes *drops a retry that arrives long after the first attempt*
fail with `a retry two months later was stored a second time`. Run it before
believing any of this.
