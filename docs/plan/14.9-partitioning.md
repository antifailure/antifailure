# 14.9, partitioning: the design decision it needs first

Written after building it and finding that it does not work as specified. The
code is not in the tree; this is what was learned, so that whoever picks it up
starts from the problem rather than from the same dead end.

## What was built

A migration converting `events` to monthly range partitions on `received_at`,
a partition manager that creates months ahead and drops months entirely past a
retention cutoff, and an archival reader that streams a partition out in
batches. Sixteen tests against a real Postgres, all passing.

## Why it is not in the tree

Postgres cannot enforce a unique constraint that does not include the partition
key. Ingestion depends on exactly such a constraint:

    INSERT INTO events (...) VALUES (...)
    ON CONFLICT (org_id, idempotency_key) DO NOTHING

That constraint is what makes a retry safe. An engine that sent a batch and lost
the response has no way to know which half landed, so it sends the same batch
again and the second copy is dropped by the database rather than by anything the
sender has to get right. It is the property twelve ingestion tests are about.

Partitioning by `received_at` forces the constraint to become
`(org_id, idempotency_key, received_at)`, and `received_at` differs between the
first attempt and the retry. The conflict never fires and every retry duplicates.

The failure was loud, which is the only good thing about it: twelve tests went
red immediately with "there is no unique or exclusion constraint matching the
ON CONFLICT specification". It would have been far worse to discover that
duplicates had been silently accepted.

## The options, and what each costs

**A separate key table.** Keep `events` partitioned and move the uniqueness to a
small unpartitioned `event_keys(org_id, idempotency_key)` written in the same
transaction. Idempotency stays exact. The cost is a second write per event and a
table that itself grows without end, which is the problem partitioning was for,
although at a fraction of the width.

**Per-partition idempotency.** Accept that a duplicate is only caught within the
month it arrived in. Since `received_at` is assigned by the server at insert,
both attempts land in the same month except for a retry that straddles a month
boundary. That is a narrow and real weakening, and it should be measured rather
than assumed before anybody relies on it.

**Partition on something already in the key.** There is no such column.
`idempotency_key` is opaque and `org_id` is not time ordered, so neither gives
partitions that can be dropped by age, which is the entire point.

**Do not partition events.** Manage size with retention deletes and accept the
bloat, or move old rows to an archive table on a schedule. The operations that
hurt are exactly the ones this avoids, so this is the option to reject last.

## What was kept

One thing from the attempt is in the tree, because it is a real gap and does not
depend on the decision above: the cross-tenant and schema suites filtered tables
on `relkind = 'r'`. A partitioned table's parent has relkind `'p'`, so the first
table anybody partitions would silently drop out of the isolation suite
altogether, and nothing would say so. They now match both.
