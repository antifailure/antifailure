The refusal that told a Heroku user to run a statement Heroku has no role for.

`AF-DB-035` is what the `pgurl` provider returns when the host server's role may
not create databases, and it ends "Run: ALTER ROLE {role} CREATEDB". That is the
right answer on a server you administer. It cannot be carried out on most of the
managed Postgres this provider gets pointed at. Heroku Postgres provisions one
database per add on and hands out no superuser at all, so there is no role that
could run the statement. A Tiger Cloud service holds exactly one database and
Tiger's own troubleshooting page says so. On either of them the engine spent the
reader's time on an impossible instruction, and the cost is not cosmetic: they
try it, it fails on a permission error, and the tool has told them to do
something that cannot be done instead of telling them the thing that works.

The thing that works was already in the provider's own header and nobody had
written it down for a vendor. `pgurl` needs TWO servers. The vendor is the
SOURCE, read once per refresh by `pg_dump`, which needs read access and nothing
else. The HOST SERVER, where the goldens and the branches are made, is a
different server that the header says should not be production. So a vendor that
refuses `CREATE DATABASE` is not a vendor this engine cannot serve. It is a
vendor that cannot ALSO be the host server, which is a smaller and truer claim
than a row of ticks would have made.

## The row this is, and why it is not thirteen providers

L2.7 gave one row to thirteen managed Postgres vendors. The failure that row is
written against is thirteen thin providers that each call `pgurl` and add a name
to a list: code volume wearing the clothes of coverage, compiling, looking like
thirteen integrations, doing nothing the one provider underneath was not already
doing.

So this is a decision per vendor with the evidence attached. Eleven of them need
nothing built and `pgurl` serves them. One, Xata, earned a provider and got one.
One, Tembo Cloud, no longer sells managed Postgres. Every verdict was read from
the vendor's own current published documentation on 2026-09-08, and every one of
them carries the page and the date in `engine/internal/db/managed/vendors.go`.

### The three outcomes, with all thirteen placed

**Native branching that is really branching, and earned a provider: one.**

- **Xata.** A storage level copy on write snapshot, on CloudNativePG and
  OpenEBS, documented as completing in seconds at terabyte scale. Apache 2.0 and
  self hostable. It has a provider in this pull request and it declares
  `CopyOnWrite: true`, which is the honest declaration and is not yet proved.

**Something in between, a fork or a point in time restore that is faster than a
dump and a restore and is not branching: eight.**

- **Crunchy Bridge**, `POST /clusters/{id}/forks`, a point in time copy that
  cannot run until an initial backup exists.
- **Aiven**, `service_to_fork_from`, from the latest backup or a point in time.
- **DigitalOcean**, `POST /v2/databases` with `backup_restore`. Its own page says
  forking "copies the source cluster's data" and "takes longer than creating a
  new cluster".
- **Heroku**, a snapshot fork, "several minutes to several hours, depending on
  the size of your dataset".
- **Fly Managed Postgres**, `POST /v1/postgres/{id}/fork`, provisioned
  asynchronously, mechanism not published.
- **Render**, point in time recovery that spins up a new instance. No fork call
  and no API for it in the documentation.
- **Tiger Cloud on its paid tiers**, backup restore plus WAL replay, "typically 5
  to 20 or more minutes".
- **PlanetScale Postgres from a backup**, which its own page calls a branch.

**No mechanism, so the `pgurl` shell is the whole answer: four.**

- **Railway.** No database branching. Its environment fork copies services and
  not data.
- **Nile.** No branching in the documentation and none in the CLI. A restore is a
  support request into a separate schema.
- **Prisma Postgres.** Daily backups with point in time recovery, no branching of
  a live database documented.
- **Tembo Cloud.** The managed Postgres was withdrawn. The company now sells
  agent orchestration and no database product appears on its site.

Tiger Cloud is the one vendor whose answer differs between its own tiers: free
services fork through copy on write in 30 to 90 seconds and standard services
restore a backup. The split is recorded rather than rounded, because rounding it
either way publishes one tier's number for the other product.

## What changed in the engine

`AF-DB-037`, a second refusal for a host server whose role lacks `CREATEDB` and
whose vendor's own documentation says the grant is unavailable. It names the
vendor, gives the remedy that works, and quotes the page and the date the verdict
was read from, because a verdict about somebody else's product goes stale and a
reader has to be able to check it. `AF-DB-035` is unchanged and is still what an
unrecognised host gets, because `ALTER ROLE` is the correct answer on a server
somebody administers, which is most of them.

`af start`'s database rung names the vendor and blocks on a documented no. It
adds nothing to the ordering and the comment says so: `pgurl.New` probes the role
at construction and refuses before `RefreshGolden` reads anything, so the dump
was already safe. What the rung adds is an answer WITHOUT CONNECTING, to somebody
who has not finished configuring yet.

`engine/internal/db/managed` is the registry. Three questions per vendor, each
with a three valued verdict, because a boolean would have forced every
unverifiable question into the flattering direction. Four vendors answer
`unverified` and it is not a polite no.

The registry and the documentation page hold the same thirteen verdicts written
twice, so three tests join them: every vendor is on the page, the page's copy on
write column matches the field, and the page's host server column matches the
verdict. Without that join a vendor could be corrected in the code and left
wrong on the page, and the page is the half a person reads before deciding
whether to try this at all. The join is a test rather than a generator because
the page is mostly prose, and prose that lives in Go string literals stops being
edited.

One function was written and deleted before this was opened. `ServedBy` turned a
host server verdict into a sentence, it read well, and nothing outside its own
test ever called it. A function with only a test caller is the dead code this
repository keeps finding in its own work, and the sentences it produced were
already written where they are used.

## Heroku cannot be recognised, and that is Heroku

A Heroku Postgres host is an EC2 name of the form
`ec2-ADDRESS.compute-1.amazonaws.com`, which is the name every other machine on
EC2 also carries. No suffix identifies one without also claiming every self
hosted Postgres on an EC2 instance, and a wrong recognition is worse than none:
it would attach Heroku's refusal to somebody whose own server does grant
`CREATEDB`. So the vendor with the strongest documented refusal on this row is
the one the engine cannot warn about from a hostname, and that is written down on
the page rather than left to be found.

## The honesty boundary

**A fake control plane over a real local Postgres proves a provider's logic, its
request shapes and its error mapping. It does not prove the vendor accepts those
requests, and it cannot produce a wall clock number.**

For this row, only the first half was ever available and for most of it not even
that. No account was created on any of the thirteen services, no request was sent
to any of their control planes, and no database was branched on any of them. What
is proved here is the engine's own behaviour: the registry, the two refusals and
the `af start` rung run against a real Postgres and are mutation tested. What is
NOT proved is that any of the thirteen vendors behaves as its documentation says,
and no number in this pull request was measured against a vendor.

## The Xata provider, and what its copy on write declaration is worth

`engine/internal/db/xata` is modelled on the Neon provider rather than invented,
because the model is the same one: the project holds production on its root
branch, a golden is a copy on write branch of that root masked and verified in
place, an environment is a copy on write branch of the golden, and publishing is
a rename because the attestation does not exist until after the branch was
created. Nothing is copied by the provider at any point.

Every path, field name and status code in `client.go` was read from Xata's own
published reference on 2026-09-08 and none of it was inferred from how a
branching service usually looks. That distinction was the whole of my original
objection to building this: a fake control plane speaking endpoints somebody
invented proves the provider agrees with its author's idea of the vendor, which
is the same defect as a twin built from a guessed stack. Xata publishes a
concrete OpenAPI reference with create, list, get, rename, delete and credentials
for a branch, so the fake speaks a real contract.

Three capabilities are declared FALSE and each is a refusal rather than a gap.
Reset, because Xata publishes no endpoint returning a branch to another branch's
state and a delete plus a recreate would hand back a different branch on a
different connection string. Subsetting, because a candidate already holds the
whole database and a subset could only mean deleting down. Pooled endpoints,
because the credentials endpoint returns one connection string and documents no
pooled variant, so declaring it would make a capability out of a synonym.

`CopyOnWrite` is declared TRUE and it is not proved. Since #307 the behaviour
that can falsify the claim is two sided, so a fake control plane over one local
Postgres cannot pass it with a truthful declaration: the only way that fake can
produce a branch carrying the golden's data is `CREATE DATABASE ... TEMPLATE`,
which copies the files, and a copy is what the behaviour refuses. The three ways
out were a false declaration, a switched off behaviour, or a truthful declaration
with the measurement not made. This is the third.

The suite has no way to say that yet, which is the note this leaves for the lane
building the third verdict. What it needs is an UNPROVEN answer from
`CopyOnWrite_BranchTimeMatchesTheDeclaration`, distinct from pass and from fail,
visible in the report rather than rendering as a pass, and reachable only from
the harness declaring it cannot exhibit copy on write rather than from a provider
asking to be excused.

`TestConformance` runs `conformance.RunDatabase` unchanged against the REAL
service and skips by name without credentials, which is the shape the plan
prescribes and the shape neon and supabase already use. The fake backed suite
runs behind `AF_XATA_FAKE_SUITE=1` and is expected to fail on exactly that one
behaviour, so the refusal is a thing somebody can read rather than a claim in a
comment.
